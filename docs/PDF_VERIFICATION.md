## 2. Extraction Pipeline Architecture

The `pdf_location_extractor.py` module extracts consignee delivery locations using an intelligent multi-stage priority inspection:

1. **Inspection Order:**
   - First scans final pages (penultimate, 3rd from last, last page) where standard delivery tables reside.
   - If not conclusively verified on final pages, scans backwards from Page 3 to Page 1.
2. **Marker Recognition:**
   Recognizes GeM procurement table headers:
   - `consignees / reporting officer and quantity`
   - `consignee / delivery address`
   - `evaluation method & consignee location`
   - `evaluation schedules`
   - `location of consignee`
   - `delivery location`
3. **Structured Entity Extraction:**
   - **City:** `Bengaluru` (normalized from `Bangalore Urban`)
   - **District:** `Bengaluru Urban`
   - **State:** `KARNATAKA`
   - **PIN Code:** Validated against the postal registry range (`560001` - `560110`)
   - **Page Number:** `3`
   - **Extraction Confidence:** `0.90`
   - **Verification Status:** `VERIFIED`

## 3. Graceful Fallback & Prevention of Placeholder Poisoning

Prior to this fix, when a PDF failed download or parsing, the extractor populated `full_address` with the placeholder text `"Delivery address could not be verified from the available document."`. The normalizer mistakenly processed this error message as a raw delivery address and marked the bid `OUTSIDE_TARGET`.

### Fixed Implementation:
* Diagnostic placeholders are explicitly identified via regex patterns (`"could not be verified"`, `"unavailable"`, etc.).
* Placeholder text is excluded from geographic classification.
* If Priority 1 (PDF) lacks verified geographic entities, the engine smoothly falls back to Priority 2 (`delivery_*`) and Priority 3 (`consignee_*`), ensuring no valid Bengaluru Urban tender is dropped.
